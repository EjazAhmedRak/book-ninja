# Terraform infrastructure

This directory begins Stage 1 of `Hosting_Deployment_Design.md`: Terraform provider and state configuration. Local state is stored in persistent Floci S3 with DynamoDB locking.

## Safety model

- `local_validation = true` targets Floci at `http://localhost:4566` with a dedicated IAM identity generated by the bootstrap script.
- AWS environments leave `local_validation = false`, so authentication comes from the standard AWS credential chain (preferably AWS IAM Identity Center or CI OIDC).
- Backend configuration files containing account-specific state locations are ignored by Git. Keep the committed `.example` files as templates only.

## Local Floci validation

Start the local AWS emulator with persistent storage and IAM enforcement:

```sh
docker compose -f docker-compose.floci.yml up -d
```

The Compose configuration creates a persistent named volume and seeds the
`floci-deployer` bootstrap IAM principal. Use that principal only to create the
least-privilege Terraform state user, its S3 bucket, and the DynamoDB lock
table. Do not use its static bootstrap credentials in committed configuration.

Requires Python 3, AWS CLI, Docker Compose, and Terraform >= 1.7. Run from this directory:

```sh
python3 scripts/bootstrap_floci.py
terraform init -migrate-state -backend-config=backends/local.hcl
terraform validate
terraform plan -var-file=environments/local.tfvars
```

The script creates the versioned, public-access-blocked `book-ninja-tfstate`
bucket, `book-ninja-tflock` lock table, and `book-ninja-terraform-state` IAM user.
This user can list the state bucket, read/write its `local/` objects, and access
the lock table. It cannot provision application infrastructure; a separate
provisioning identity will be configured for the next infrastructure increment.

Generated `backend.tf`, `backends/local.hcl`, and `local.auto.tfvars.json` are
ignored by Git. Credential files are written with owner-only permissions; keys
are never printed. Rerunning the script reuses the saved active key.

The `infra_floci-data` named volume preserves IAM, S3, and DynamoDB data across
restarts. `docker compose down` preserves it; `docker compose down -v` deletes
the volume, including Terraform state. Terraform warns that DynamoDB locking
is deprecated; it is retained to follow the design's Floci locking contract.

## AWS development and production

Use a separate checkout or working directory from local Floci, without its
generated auto-loaded credentials. Create private backend files from examples:

```sh
cp backends/aws.tf.example backend.tf
cp backends/dev.hcl.example backends/dev.hcl
cp environments/dev.tfvars.example environments/dev.tfvars
# Edit backends/dev.hcl with the existing state bucket and lock-table names.
terraform init -backend-config=backends/dev.hcl
terraform plan -var-file=environments/dev.tfvars
```

Production follows the same pattern with `prod.hcl` and `prod.tfvars`. The state S3 bucket and DynamoDB lock table must be bootstrapped separately before the first remote Terraform initialization. They must be encrypted, versioned, private, and access-controlled.
